## 官版规则

官版 App 内足迹规则页已截图：

- 今日收听在进入周/月页面时刷新，显示约延迟 1～2 分钟。
- 历史总时长包括歌曲、播客、有声书，按天维度更新。
- 常规歌曲至少播放 30 秒才统计；不足 30 秒的歌曲需要完整播放。
- 多端数据会汇总，日上限 24 小时，且说明部分终端暂不支持计入。

见 `official-footprint-rules-loaded.png` 与 `official-footprint-rules-bottom.png`。规则未给出历史累计的具体每日结算时刻；不能承诺明日某个时间一定更新。

## 文档中的总收听时长地址

用户给出的 API Enhanced 文档路线为 `/listen/data/total`，需要登录。它是部署该项目的 API 服务所提供的路线，不能把文档站域名直接当作接口服务地址。

项目当前模块 `module/listen_data_total.js` 转发到 `/api/content/activity/listen/data/total`，请求内容为空。Mesting 的 `OfficialFootprintRepository.totalSeconds()` 已读取这一业务路线的 `data.totalDuration`，未将本地播放秒数上传到它。

本轮官版日志实际看到的读取地址为 `https://interface3.music.163.com/xeapi/content/activity/listen/data/total`。`/xeapi` 为观察到的官版请求形态；文档模块和现有代码使用上述 `/api` 业务路线。不能仅凭地址前缀差异宣称其为历史累计不增长的原因。

文档与源模块：

- https://neteasecloudmusicapienhanced.js.org/#/?id=%e5%90%ac%e6%ad%8c%e8%b6%b3%e8%bf%b9-%e6%80%bb%e6%94%b6%e5%90%ac%e6%97%b6%e9%95%bf

## 当前官版 APK 中复核的差异

对从手机拉取的原 APK 创建三个定向分析载体。每份载体内的 AndroidManifest.xml 和原始 DEX 均与 APK 逐成员一致，见 `current-carrier-verification.json`。载体只用于局部静态分析，未安装，不代表完整 APK 调用图。

当前 9.6.15 的 `qn0.z0.q4` 在歌曲结束时调用：

```text
gs.p("play", "5dce13da9501aecff943b2ca", payload)
  → IStatistic.logJSONRealTime(action, mspm, payload)
  → payload[mspm] = 分类值; payload[lt] = 1
```

当前 `q4` 还设置真实进度、播放速度和若干依实际场景构造的字段。旧原生候选缺少歌曲结束的 mspm 分类，也没有完整重现官版开始/结束载荷及公共上下文。这一静态差异值得验证，**尚未证明单独补一个字段就能恢复历史累计**，也不能直接把 Android 分类混入已工作的桌面 weblog。

已保存的三份方法证据为 `current-songend-method-evidence.json`、`current-gsp-method-evidence.json`、`current-logjson-method-evidence.json`，完整导出为 `rea-current-official-recovered-evidence.json`，共 3 条方法证据。`gs` 在该定向载体中的 JADX 显示别名发生变化，原始选择器、载体摘要及正文分别保留。

中断后第一次新会话导出 `rea-current-official-evidence.json` 为 0 条，不能作为此前调用的证据。随后重新从原始载体复核并保存上述三条方法；本报告只引用这些已保存证据。REA 活动分析器已关闭。
