# 1.0.45 双开切歌实测与首次恢复边界

用户本轮明确同意继续覆盖安装候选、每轮最多约三分钟的脱敏采集，并进一步允许直接操作同一手机的两个已登录分身。两个 Android 用户分别为 0 与 999；测试范围先限定切歌。分身受到系统音频焦点影响而自动暂停，因此本轮任何播放/暂停数值都不作为双设备同步验收。

## R2 实机结果

R2 原签名 APK 已成功覆盖安装，设备回读 SHA-256 为 `ed450f0b68507fcdcbefeae06145b5143c3147f62d2e94c6d2c35765f3ba5c27`，与冻结候选一致。两个实例的 APK 路径相同，账号及房间恢复，未清除数据。

只读观察器和主动操作脚本分开。观察器只保存固定阶段枚举、数字/布尔、目标进程归属和媒体信息摘要，不保存原始 logcat、凭据、房间ID、私信或媒体标题。画面仅在本机私有验证目录保存。每次判断后台成功，均先读取接收端的媒体会话状态，确认摘要一致，再打开接收端；不能把恢复前台后的更新算作后台成功。

共六次成功、两次失败。前三轮阶段采集持续约 165、180、180 秒，均自动停止或由本机 STOP 文件提前结束，原始计时保留清理开销。详细白名单结果在私有 `2026-11-03-v145-dual/r2-test-results.json`。

因此已验证 R2 能修复正常媒体播放建立后的前后台切歌路径，但不能宣称后台同步全部完成。首次恢复问题可重复：接收端媒体状态为 NONE，原生阶段报告 `mediaServiceMissing`，背景脉冲在最初数秒后停止。进程仍在；某次系统进程快照的 `isFrozen` 为 false，不能把现象直接定性为 Android 系统 freezer。

## R3 有界房间唤醒租约候选

当前媒体插件只有首次进入 playing 时才建立前台媒体服务；`androidStopForegroundOnPause: false` 只保证已建立服务不因暂停退出，不覆盖从未开始播放的恢复状态。Together 原生工作线程先前又把自己的有界唤醒锁绑定到该前台媒体服务是否存在，导致有效房间的接收能力依赖此前是否播放过一次。

R3 仅调整原生工作线程的唤醒归属：有效后台房间租约期间持有原有有界锁，媒体服务是否存在继续记录为诊断信息；仍由租约失效、退出、回前台和引擎销毁释放。没有修改播放状态、构造静音音乐、增加服务/通知或系统权限。此改动先作为待验证候选，不把唤醒锁等同于前台服务，也不承诺防止系统杀进程。

原有十项 JVM 调度/诊断场景及 Android/Flutter 类型检查重新通过，R3 已构建、原签名核验、覆盖安装并回读实际 APK 摘要。实机首次恢复复核再次失败：原生已记录唤醒锁取得，但接收端在后台仍停留旧曲，脉冲仍在数秒后停止。因此 R3 被否决，不能把唤醒锁取得算作可持续后台执行；该单独改动将撤回。Dart、页面、接口协议和 R2 快照修复保持。

后续只调查现有 AudioService 的前台承载：当前固定版本只在首次进入 playing 时建立前台媒体服务，尚未播放的恢复状态没有该承载。需在有效后台房间中复用同一服务和音乐通知，并保留真实播放状态与退出清理，不能通过虚假播放或静音音源保活。R4 尚未实现或验证。
